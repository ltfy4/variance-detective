Variance Detective · deployment handbook · v0.1

Putting an evidence-backed variance agent into a finance team

Everything needed to install, connect, secure, run and roll out Variance Detective in a company — from an analyst's laptop to a scheduled service on AWS Bedrock or Azure OpenAI.

1 · What you are deploying

Variance Detective answers one question — why did this KPI move against plan? — and answers it in a way finance can audit. It reads facts from any planning or ERP system through MCP, decomposes the variance deterministically, writes a narrative in which every number is cited to an evidence id and machine-verified, remembers what it found last month, and drafts a forecast adjustment that a human approves.

What goes to the model

A compact JSON of the variance tree: node labels, rounded values, pre-formatted display strings and evidence ids. Never raw rows, never credentials, never the whole dataset.

What the model may do

Explain. It cannot compute, cannot write to a system, and cannot state a number that is not in the evidence — the verifier flags anything that slips.

What stays on your side

All data, the evidence ledger, memory (SQLite), proposals (JSON) and reports — in workspace/ or wherever you mount it.

3 · Install in 15 minutes (topology A)

  1. Prerequisites Python 3.11+ (3.12 recommended), git, and for SAC-MCP: uv (pip install uv). Windows, macOS and Linux all work.
  2. Get the code
    git clone <repo> variance-detective && cd variance-detective
python -m venv .venv && source .venv/bin/activate     # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
  3. Prove the engine offline
    vd demo --open
    Two investigations run on the synthetic retailer: February seeds memory, March finds three South stores with margin-rate erosion, flags S07 as recurring, drafts a Plan PR, and opens the HTML report. No keys, no network.
  4. Run the tests pytest — 19 tests including a live MCP round-trip through a fake server.
  5. Add a model (section 4) and connect your first system (section 5). Both are configuration.
  6. First real investigation
    vd sources test sac
vd investigate --kpi gross_margin --period 2026-03 --source sac --open

4 · Choose and wire the model

One provider class per vendor sits behind a single complete() call. Choose with llm.provider in config/agent.yaml, or override per run with --provider/--model, or via environment: VD_LLM__PROVIDER, VD_LLM__MODEL. Secrets are read by the vendor SDKs from the environment only.

Amazon Bedrock (recommended for AWS-first companies)

  1. Enable model access in the Bedrock console for the region you will use (e.g. eu-west-2); for cross-region resilience use an inference profile ARN as the model id.
  2. Create an IAM role for the runner (ECS task role / EC2 instance role / your SSO role) with deploy/aws/bedrock-iam-policy.json — invoke rights on the approved model ARNs only, read on the agent's secrets, write on the report bucket.
  3. Configure
    pip install -e ".[bedrock]"
export AWS_REGION=eu-west-2            # or AWS_PROFILE=finance-ai
export VD_LLM__PROVIDER=bedrock
export VD_LLM__MODEL=anthropic.claude-sonnet-4-5-20250929-v1:0
vd demo
  4. Harden Put Bedrock behind a VPC interface endpoint (PrivateLink) so prompts never traverse the public internet; enable Bedrock invocation logging to CloudWatch/S3 for audit; attach Bedrock Guardrails if your AI policy requires it.

Azure OpenAI (recommended for Microsoft-first companies)

  1. Create an Azure OpenAI resource in an approved region and deploy a model (e.g. gpt-4o); note the deployment name.
  2. Auth Simplest: an API key in Key Vault surfaced as AZURE_OPENAI_API_KEY. Preferred: Entra ID managed identity — assign Cognitive Services OpenAI User to the runner identity and swap the key for azure_ad_token_provider in llm/providers.py (a 5-line change, documented inline).
  3. Configure
    pip install -e ".[azure]"
export AZURE_OPENAI_ENDPOINT=https://<resource>.openai.azure.com
export AZURE_OPENAI_DEPLOYMENT=gpt-4o
export AZURE_OPENAI_API_KEY=...        # or managed identity
export VD_LLM__PROVIDER=azure_openai
vd demo
  4. Harden Private endpoint + disable public network access; Azure Monitor diagnostic logs; content filters at the default level are fine for finance narrative.

Anthropic API, local or other

# Anthropic API
pip install -e ".[anthropic]"; export ANTHROPIC_API_KEY=...; vd demo --provider anthropic --model claude-sonnet-4-5
# Local / air-gapped with Ollama (OpenAI-compatible)
pip install -e ".[openai]"; export OPENAI_BASE_URL=http://localhost:11434/v1 OPENAI_API_KEY=ollama
vd demo --provider openai --model llama3.1
# No model at all — deterministic template narrator (CI, demos, strict environments)
vd demo --provider offline
Model choice guidance. The narrative is a constrained explanation task over ~5–8k input tokens; a mid-tier model (Claude Sonnet, GPT-4o) is more than sufficient. Cost per investigation is a few cents. If a model returns malformed JSON the narrator retries once with the validation error and then falls back to the template narrator — the report says so in a visible warning, never silently.

5 · Connect planning systems

A source is two YAML blocks: its vocabulary (semantic mapping) and its transport + tool map (connector). No code.

5.1 Map the vocabulary — config/semantic_model.yaml

sources:
  sac_planning:
    dimensions: { time: Date, version: Version, region: Region, store: Store, channel: Channel, category: ProductCategory }
    measures:   { net_sales: NetSales, cogs: COGS, units: Units }       # or expressions: "GrossSales - Returns"
    members:
      version: { Actual: public.Actual, Forecast: public.Forecast }

5.2 Register the connector — config/sources.yaml

sources:
  sac:
    type: mcp
    semantics: sac_planning
    transport: stdio                     # or streamable_http / sse with url + headers
    command: uvx
    args: ["sac-mcp"]
    env: { SAC_TENANT_URL: "${SAC_TENANT_URL}", SAC_CLIENT_ID: "${SAC_CLIENT_ID}", SAC_CLIENT_SECRET: "${SAC_CLIENT_SECRET}" }
    capabilities: { write_draft: true }
    operations:
      describe:   { tool: get_model_metadata, arguments: { model_id: "${SAC_MODEL_ID}" } }
      read_facts:
        tool: read_fact_data
        arguments: { model_id: "${SAC_MODEL_ID}", filters: "{filters}", measures: "{measures}", dimensions: "{dimensions}" }
        result_path: data
      write_draft:
        tool: upload_job_data
        arguments: { model_id: "${SAC_MODEL_ID}", version: "{target_version}", rows: "{rows}" }

Placeholders: {filters} → {source_col: [members]}, {measures}, {dimensions}, {filter_first:Version}. The connector re-applies filters locally after the call, so a server that ignores a filter still yields correct numbers.

Writing your own connector for an unusual API is ~40 lines: subclass DataConnector, implement _read_source(query) returning a DataFrame in the source's own column names, register it in connectors/registry.py. Mapping, aggregation, evidence and everything downstream are inherited.

6 · Security & governance

Identity & least privilege

One service identity per environment. Read-only on the planning model for investigation; a separate identity with write scope on a draft version for vd pr apply.

Secrets

Never in YAML. Environment variables injected from Secrets Manager / Key Vault / Vault at runtime; .env only on laptops and git-ignored.

Network

Model endpoints over PrivateLink / private endpoints; MCP servers over stdio in the same container or over HTTPS inside the VPC/VNet with mTLS or bearer tokens.

Data minimisation

The model receives aggregated node values and display strings, not row-level data. Evidence tables are capped at 25 rows in reports (reporting.evidence_rows_limit).

Human in the loop

Writes are proposals (workspace/proposals/*.json). vd pr approve --by records identity + timestamp; only approved proposals can be applied; only to the configured draft version.

Audit trail

The JSON report is a full record: request, tree, every evidence table, the narrative with per-claim verification, model id, token usage, timings, warnings. Keep it in object storage with retention.

Policy checklist before go-live: AI usage policy signed off for the chosen provider · data classification confirmed (financial, internal) · DPIA not required unless employee-level data is in scope · model region matches data-residency rules · report storage has retention and access control · an owner is named for approving Plan PRs.

7 · Run it monthly

Schedule

Run on working day 2–3 after close for each KPI × entity you report on. One vd investigate per KPI; add --scope entity=UK for entity packs. Example cron: 0 6 3 * * cd /opt/vd && vd investigate --kpi gross_margin --period $(date +%Y-%m) --source sac. Airflow DAG in deploy/airflow/.

Distribute

HTML reports are self-contained (no scripts, light/dark, print-ready). Post to SharePoint/Confluence, attach to the close deck, or push the Markdown into the commentary field of your planning tool. For Teams/Slack, post the headline + link via their MCP server or webhook from the scheduler.

Monitor these four numbers

MetricWhereHealthy
Verification scoreverification.score in the JSON report1.0 (template) · ≥ 0.9 (LLM); investigate any drop
Fallback ratellm.fallback present< 5 % of runs
Fetch timetimings_ms.fetchStable month to month; a jump means a source changed

Review prompts like code

Prompts live in one file (agent/prompts.py). Changes go through pull request with the demo and tests as regression; the verifier is your safety net for prompt drift.

8 · Containers & cloud

docker build -t variance-detective .
docker run --rm -v $PWD/workspace:/app/workspace -e VD_LLM__PROVIDER=offline variance-detective vd demo
docker compose up api            # http://localhost:8080/docs — POST /investigate, GET /proposals

AWS

Push the image to ECR. Run as an ECS Fargate scheduled task (EventBridge rule, monthly) for topology B, or as a Fargate service behind an internal ALB with IAM/SSO for topology C. Task role = deploy/aws/bedrock-iam-policy.json; mount EFS or sync /app/workspace to S3 after each run. Secrets via Secrets Manager → task definition secrets.

Azure

Push to ACR. Topology B: Azure Container Apps Job on a cron trigger (or Azure Data Factory custom activity). Topology C: Container Apps app with managed identity, Easy Auth (Entra) in front, Key Vault references for secrets, Azure Files mounted at /app/workspace.

Anywhere else

It is a plain Python process: Kubernetes CronJob, GitHub Actions on a schedule (demo runs there today), or a VM with cron all work.

9 · Six-week rollout plan

  1. Week 1 — Prove on an export. Export last quarter's actual + forecast to CSV, map it as a csv source, run three months in sequence so memory builds. Success: the agent finds the drivers the team already knows.
  2. Week 2 — Connect the live system (read-only). Service identity, MCP source, vd sources test. Success: identical numbers to the export.
  3. Week 3 — Add the model. Bedrock or Azure. Compare LLM narrative vs template on the same evidence; tune prompts. Success: verification ≥ 0.9, analysts prefer the prose.
  4. Week 4 — Shadow the close. Run on WD3 alongside the manual commentary. Success: ≥ 70 % of manual explanations appear in the report; time-to-commentary halves.
  5. Week 5 — Plan PR in anger. Review the drafted adjustments in the forecast meeting; approve/reject in the tool; apply to a draft version. Success: at least one approved proposal applied without manual re-keying.
  6. Week 6 — Productionise. Container, schedule, monitoring, report distribution, owner for proposals. Hand over with this handbook and the architecture doc.

A sibling agent

Every agent in this family shares connectors, semantic model, evidence ledger, memory, verifier and reporting. A new agent is a new analysis/ module (the deterministic skill) and a narrator template. Candidates, in order of value: Forecast Integrity (bias scoring), Reconciler (which number is right), Cycle Operator (budget season PMO), Model Guardian (model change impact). They can cite each other's evidence ids because the ledger is just ids and tables.

FAQ

Does the model see our data? It sees aggregated node values and formatted strings for the nodes in the tree — typically a few hundred numbers — never row-level rows. With Bedrock/Azure private endpoints nothing leaves your cloud boundary.

Can it run without any model? Yes — --provider offline uses the template narrator, which produces fully verified prose. Many teams start there.

Can it change our forecast? Only through a Plan PR that a named person approves, and only to the draft version you configure.

What if two systems disagree? That is the next agent (Reconciler). Today you can run the same investigation against two sources and compare the headline evidence.
